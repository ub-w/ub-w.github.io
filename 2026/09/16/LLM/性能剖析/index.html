性能剖析

性能优化之前必须先进行性能剖析（profiling）。剖析不是收集越多指标越好，而是用证据回答：程序哪里慢、哪个 kernel 重要、它为什么慢，以及应该优化什么。

一、性能剖析流程

问题 查看内容 现代工具
时间花在哪里？ 时间线、CPU↔GPU 数据复制、Kernel、同步等待 Nsight Systems
哪个 kernel 最重要？ 总耗时、调用次数、单次耗时 Nsight Systems
kernel 受什么限制？ Compute / Bandwidth / Latency Nsight Compute
哪项资源有问题？ DRAM、Cache、执行管线、Occupancy Nsight Compute
warp 为什么停顿？ Stall Reasons、Source Counters Nsight Compute

分析分为两个层次：Nsight Systems 查看整个应用，回答“时间花在哪里”；Nsight Compute 深入单个 kernel，回答“为什么慢”。

二、优化前先正确测量

优化代码之前，要先完成两件事：

  1. 明确测量范围：测整个程序的端到端时间，还是只测某个 kernel 的执行时间；
  2. 保存优化前的数据：把当前版本的耗时和测试条件记录下来，作为之后比较的起点。

这个“优化前的比较起点”就叫做性能基线（performance baseline）。例如：

三、应用级分析：时间花在哪里

1.用 Timeline 查看工作如何排列

**Timeline（时间线）**按照发生时间展示 CPU 调用、数据复制和 GPU kernel。它首先回答的不是“某个 kernel 为什么慢”，而是“整个程序的时间到底花在了哪里”。

这张图可以分成两部分看：

  • 上半部分 Timeline：横轴是时间，不同轨道展示 CUDA API、Memcpy 和 kernel 是否串行或重叠；
  • 下半部分 Analysis：工具根据时间线给出提示，例如复制与计算重叠较少、计算利用率较低；
  • 这些提示只是后续调查方向，不能脱离程序依赖关系直接当作优化结论。

时间线可以看到：

  • CPU 何时调用 CUDA API；
  • HtoD、DtoH 何时执行；
  • kernel 何时开始和结束；
  • 不同 stream 是否并发；
  • CPU 和 GPU 何时等待；
  • 数据传输是否与计算重叠。

对于前面的同步向量加法示例，一种典型时间线是：

所有操作串行执行，没有 memcpy/kernel overlap。

低重叠不一定就是 bug。若只有一批数据，且 kernel 必须等待输入、输出必须等待 kernel，天然存在依赖。要形成流水线，通常需要把数据拆成多个 chunk，并结合 pinned memory、cudaMemcpyAsync 和多个非默认 stream。

更优先的问题通常是：能否让数据持续驻留在 GPU，从根本上减少 CPU↔GPU 往返。

2.找到真正重要的 kernel

Profiler 会按执行时间和调用情况排列 kernel。阅读时要区分：

  • 单次最慢的 kernel；
  • 累计时间最多的 kernel；
  • 整个应用真正的瓶颈。

如果 vecadd_kernel 是一次运行中唯一的 kernel，它自然会在 kernel 排名中位列第一；但还必须回到应用时间线检查它在端到端时间中的占比。若它只占整体时间的 2%，排名第一也不意味着应该优先微调它。

这体现了 Amdahl 定律：整体加速效果受“被优化部分在总时间中的占比”限制。如果一个 kernel 只占总时间的 2%，即使把它的耗时完全消除，整体时间也最多减少约 2%。

四、Kernel 级分析：为什么慢

1.查看启动配置与资源用量

课程使用的 NVVP 界面如下。先在中间的 kernel 列表或上方时间线中选中 vecadd_kernel，然后查看右侧的 Properties 面板：

图中右侧面板分成两类信息：

  • 启动信息：Duration、Grid Size、Block Size 和 Stream；
  • 资源信息：Registers/Thread、Shared Memory/Block 和 Occupancy。

常见字段含义如下：

属性 含义
Duration kernel 在 GPU 上的执行时间
Stream 所属 CUDA stream
Grid Size grid 中 block 的数量
Block Size 每个 block 的线程数量
Registers/Thread 每线程寄存器用量
Shared Memory/Block 每 block 共享内存用量
Achieved Occupancy 运行时实际平均 occupancy
Theoretical Occupancy 根据资源计算的理论上限

以 N = 2^27、每个 block 512 个线程的向量加法为例，可以直接推导出 grid 大小为 ceil(N / 512) = 262144。但 Registers/Thread 要看编译结果，Achieved Occupancy 要靠实际运行测量，不能从源码或课堂中的一次结果直接推广。

2.分析 Occupancy 及其限制因素

Occupancy 是每个 SM 上活跃 warp 数相对于硬件最大活跃 warp 数的比例。

这张图不是只给出一个 Occupancy 百分比，还分别列出了：

  • 当前每个 block 的线程和 warp 数；
  • 每线程、每 block 的寄存器用量；
  • 每 block 的共享内存用量；
  • 线程、寄存器、共享内存和 block 数上限分别允许多少活跃 block。

真正要找的是哪一项资源先达到上限，因为它决定一个 SM 最终能同时驻留多少个 block。

Profiler 会分别计算线程、寄存器、共享内存和硬件 block 上限允许多少驻留 block，最终取最小值：

在这些明确的假设下，理论 occupancy 可以达到 100%。实际设备限制和编译后的寄存器用量必须从设备资料与 profiler 报告获得。

Block 大小的影响

  • 每 block 的 warp 数；
  • 每 SM 可驻留 block 数；
  • 寄存器和共享内存的分配；
  • 调度粒度与尾部效应；
  • 某些算法的 tile 大小和数据复用。

block 越大不代表 occupancy 越高。通常测试 128、256、512 等 32 的整数倍，并以实际运行时间判断。

如果一个 block 只有 32 个线程，它正好是一个 warp；但在每 SM 最大驻留 block 数有限的设备上，可能因为 block 数上限而无法填满全部 warp。例如最多驻留 32 个 block、64 个 warp 的 SM，只能得到 32 个驻留 warp，即最高约 50% occupancy。

高 occupancy 也不保证高性能。只要活跃 warp 已足够隐藏延迟，继续提高 occupancy 可能没有收益。

3.判断 Compute、Bandwidth 或 Latency Bound

类型 常见表现 后续检查
Compute bound 某类计算管线利用率高 指令构成、功能单元
Memory bandwidth bound Device Memory 利用率高 事务、带宽、Cache、访存模式
Latency bound 计算和带宽都不高，但 warp 频繁等待 Stall Reasons、依赖、Occupancy

图中的计算利用率明显低于 Device Memory 利用率，因此工具把这个 vecadd_kernel 判断为更可能受到显存带宽限制。这个结论只适用于图中这次运行，换输入规模或 GPU 后需要重新测量。

向量加法的算术强度很低，因此在数据规模足够大、访存规整且执行开销被摊薄时，通常容易受显存带宽限制；是否已经达到该状态，仍应由实际 profiler 数据确认。

4.Memory Bandwidth 与 Memory Statistics

Profiler 可以沿内存层次查看：

在这张报告中，应当按内存层次逐级看带宽和事务：Shared Memory、L2 Cache、Unified Cache、Device Memory 和 System Memory。图中 Device Memory 的利用率最高，所以后续应重点检查显存流量是否必要、访问是否合并，以及数据是否能够复用。

常见数据包括：

  • memory instructions；
  • memory requests / transactions；
  • 读写字节数；
  • 各层带宽和利用率；
  • cache hit rate；
  • local memory、atomic、texture 和 shared memory 流量。

可以先用下面的简化关系理解这些统计量：

  • Memory instruction：warp 执行了一条 load 或 store 指令；
  • Request：这条指令产生的逻辑访存请求；
  • Transaction：内存层次为了满足请求而进行的实际数据传输；
  • Transferred bytes：这些 transaction 实际搬运的数据量。

地址越分散，一条访存指令通常会被拆成越多 transaction，因此实际搬运的数据可能明显多于程序真正使用的数据。

如何阅读

向量加法为什么容易带宽受限

每个元素执行：

算术强度大约是 1 FLOP / 12 Byte。

计算很少、数据移动很多，所以通常受显存带宽限制。

展开：使用 N = 2^27 验证理论数据量与指令数

假设 N = 2^27 = 134217728。

理论读取量为 2 × N × 4 Byte = 1 GiB。

理论写入量为 N × 4 Byte = 512 MiB。

如果 profiler 中 L2 与 Device Memory 间的流量也接近读取 1 GiB、写入 512 MiB，才可以据此判断没有明显额外流量。

总 warp 数为 N / 32 = 4194304。

每个 warp 执行两条 load 和一条 store，所以大约执行 4194304 × 3 = 12582912 条内存指令。

即约 12.59 million 条 warp 级内存指令。如果报告值与之接近，而且实际传输字节接近理论值，就能为“访存模式比较规整”提供证据。

对于这种单独的流式向量加法，共享内存没有数据复用价值。更有效的方向是算子融合、降低数据精度和避免中间张量反复写回显存。

5.Compute Resource Utilization

Profiler 可以查看不同功能单元的利用率：

图中上半部分表示 Load/Store、算术和控制流等功能单元的利用程度；下半部分表示不同类型指令在已执行指令中的占比。两张图需要结合阅读：指令占比高不等于对应执行管线已经成为瓶颈。

  • Load/Store；
  • FP16、FP32、FP64；
  • Integer；
  • Special Function；
  • Control-Flow；
  • Texture。

还可以查看指令构成和 inactive/predicated-off 线程，用来分析：

  • 某类执行管线是否饱和；
  • 整数索引计算是否过多；
  • load/store 是否占比很高；
  • 控制流和 warp 分歧是否明显；
  • 是否执行了大量无效指令。

需要注意：指令数量占比不等于耗时占比。某类指令很多，不代表它一定是性能瓶颈，还要结合管线利用率和 stall 情况。

6.Latency Analysis

当 warp 当前不能发射下一条指令时，profiler 会统计 stall reason。

这张图表示采样到的 warp 停顿主要来自 memory dependency，也就是下一条指令依赖尚未返回的内存数据。饼图只能告诉我们等待类型的占比，还需要结合吞吐量、Occupancy 和具体源码判断它是否是主要瓶颈。

Stall Reason 含义
Memory Dependency 等待 load 返回的数据
Execution Dependency 等待前一条计算产生结果
Instruction Fetch 等待取指令
Not Selected warp 已就绪，但调度器选择了其他 warp
Memory Throttle 内存请求队列或管线压力过高
Pipe Busy 所需执行管线正在忙
Synchronization 等待 barrier 等同步操作
Constant / Texture 等待相应内存路径的数据

Not Selected 不一定是坏事，它可能说明调度器拥有很多可执行 warp。Stall 指标必须与吞吐量、eligible warps 和源码一起分析，不能看到占比高就直接认定为瓶颈。

PC Sampling 或现代 Nsight Compute 的 Source Counters 可以将 stall 定位到源码、PTX 或 SASS 指令。

五、从分析到优化验证

1.应用层

  1. 端到端时间是多少？
  2. Memcpy、kernel、同步分别占多少？
  3. CPU 和 GPU 是否存在大段空闲？
  4. 复制和计算是否可能重叠？

2.Kernel 层

  1. 哪些 kernel 的累计耗时最高？
  2. 是 compute、bandwidth 还是 latency bound？
  3. grid、block、寄存器和共享内存配置如何？
  4. Occupancy 被什么资源限制？
  5. 内存事务和实际字节是否符合算法预期？
  6. 哪种执行管线利用率最高？
  7. warp 主要因为什么停顿？

3.优化验证

  1. 每次只修改一个主要因素；
  2. 保留优化前的性能基线；
  3. 验证数值正确性；
  4. 使用非 profiling 运行重新测量；
  5. 检查瓶颈是否已经转移。

nvprof 和 NVVP 已被弃用，并已从 CUDA 13.0 移除，因此这里只保留它们来帮助阅读旧资料；新的实验应迁移到 Nsight 工具。移除信息可在 CUDA 13.0 Release Notes 中核对。

旧工具或界面 现代工具 主要用途
nvprof 时间摘要 nsys stats CUDA API、kernel 和 memcpy 汇总

Instruction / PC Sampling Nsight Compute Source 指令、源码和 stall 定位
展开：阅读旧课程时需要的 nvprof / NVVP 命令

命令行摘要：

输出中的 GPU activities 表示 GPU 上实际发生的 memcpy 和 kernel；API calls 表示 CPU 调用 CUDA Runtime API 所花的时间。cudaDeviceSynchronize 的 API 时间通常表示 CPU 正在等待此前提交的 GPU 工作，并不是 GPU 执行了一个同名计算任务。

常见字段：

字段 含义

Time 累计时间
Calls 调用次数
Avg 平均时间
Min / Max 最短和最长时间
Name 活动、kernel 或 API 名称

生成时间线与硬件指标报告：

timeline.prof 用于寻找时间花在哪里，metrics.prof 用于分析 kernel 为什么慢。

Profiling 不等于 Benchmark

GPU 硬件计数器数量有限，收集大量 metrics 时，profiler 可能多次 replay 同一个 kernel。此时采集期间的运行时间不能作为真实性能结果。实际使用时应只收集与当前假设有关的指标，并尽量限定 kernel 或代码范围。

ncu --set full 也可能 replay kernel，因此同样不能把 profiling 运行时间当作正式 benchmark。

七、总结

  • 性能剖析首先建立可靠基线；kernel launch 具有异步性，计时必须处理同步边界。
  • Nsight Systems 用于分析整个应用的时间线，先找出 memcpy、kernel、同步和 CPU 等部分的耗时。
  • Nsight Compute 用于深入关键 kernel，分析启动配置、Occupancy、内存、计算管线和 warp stall。
  • Kernel 排名必须结合端到端占比理解，排名第一不等于值得优先优化。
  • 判断瓶颈时先区分 compute、bandwidth 和 latency bound，再检查对应指标与源码。
  • Profiling 用来解释行为，benchmark 用来比较性能；优化后必须使用正常运行重新计时。
